# 规则引擎通用能力边界说明 V1.0

## 一、文档说明

本文档明确规则引擎的功能边界、能力范围、技术限制和扩展性，帮助业务方和开发团队理解系统的能力和局限性。

---

## 二、规则引擎核心定位

### 2.1 核心能力

规则引擎是一个**通用的业务规则执行平台**，专注于：

1. **条件判断**: 基于输入数据进行复杂的条件匹配
2. **规则执行**: 当条件满足时，执行预定义的动作
3. **结果返回**: 将执行结果返回给业务系统
4. **规则管理**: 提供可视化的规则配置和管理界面

### 2.2 设计理念

- **业务无关**: 规则引擎不依赖具体业务，通过适配器模式接入
- **配置驱动**: 业务规则通过配置实现，无需修改代码
- **高性能**: 支持规则预编译和缓存，保证快速执行
- **易扩展**: 支持新业务场景和新字段的快速接入

## 三、功能能力范围

### 3.1 支持的功能（✓）

#### 3.1.1 规则配置管理

✓ **规则CRUD操作**
- 创建、修改、删除、查询规则
- 规则启用/禁用
- 规则复制/导入/导出

✓ **规则版本管理**
- 规则版本记录
- 版本回滚
- 版本对比

✓ **规则分组管理**
- 规则组创建和管理
- 规则组层级结构
- 规则组执行模式（ALL/FIRST）

✓ **规则优先级控制**
- 通过priority字段设置优先级
- 高优先级规则优先执行

#### 3.1.2 条件表达式

✓ **基础比较操作**
- 等于、不等于
- 大于、大于等于、小于、小于等于
- 范围判断（between）

✓ **集合操作**
- 包含（in）、不包含（not in）
- 数组包含元素、数组不包含元素

✓ **字符串操作**
- 左匹配（startsWith）
- 模糊匹配（正则表达式）
- 包含子串、不包含子串

✓ **空值判断**
- is null、is not null

✓ **逻辑组合**
- AND逻辑（所有条件必须满足）
- OR逻辑（任一条件满足）
- AND/OR嵌套组合（多层嵌套）

✓ **复杂条件组**
- 支持多个条件组
- 条件组内部AND，条件组之间OR（或相反）

#### 3.1.3 数据类型

✓ **基本数据类型**
- String（字符串）
- Number（数值：整数、小数）
- Boolean（布尔值）
- Date（日期时间）
- Array（数组）
- Object（对象/Map）

✓ **类型自动转换**
- 字符串转数值
- 字符串转日期
- 宽松类型匹配

#### 3.1.4 规则动作

✓ **返回结果**
- 设置输出数据
- 返回匹配的规则信息

✓ **修改数据**
- 修改输入数据（通过update）
- 触发其他规则重新评估

✓ **日志记录**
- 记录规则执行日志
- 记录匹配的规则和结果

✓ **自定义动作**
- 通过ActionHandler接口扩展
- 业务适配器可注册自定义动作

#### 3.1.5 业务适配

✓ **多业务场景接入**
- 通过BusinessAdapter接口接入
- 每个场景独立配置

✓ **数据转换**
- preProcess：业务数据转规则引擎数据
- postProcess：规则结果转业务结果

✓ **元数据配置**
- 每个场景定义自己的字段元数据
- 元数据用于前端动态渲染

✓ **计算字段**
- 支持基于其他字段计算的派生字段
- 通过compute_expression定义

#### 3.1.6 性能优化

✓ **规则预编译**
- 规则编译为Drools DRL
- 编译后缓存KieBase

✓ **缓存机制**
- 按场景缓存已编译规则
- 支持手动刷新缓存

✓ **批量执行**
- 支持批量数据并行执行
- 提高吞吐量

#### 3.1.7 规则测试

✓ **规则模拟测试**
- 输入测试数据
- 查看规则执行结果
- 查看匹配的规则

✓ **规则验证**
- 规则语法验证
- 规则编译验证
- 字段存在性验证

#### 3.1.8 监控与日志

✓ **执行日志记录**
- 记录每次规则执行
- 包含输入数据、输出数据、匹配规则
- 记录执行耗时

✓ **日志查询**
- 按场景、规则、时间范围查询
- 查看执行详情

---

### 3.2 不支持的功能（✗）

#### 3.2.1 规则引擎不负责

✗ **业务逻辑实现**
- 规则引擎不实现具体业务逻辑
- 业务逻辑应在BusinessAdapter中实现

✗ **数据持久化**
- 规则引擎不负责业务数据的存储
- 只负责规则配置数据的存储

✗ **数据查询**
- 规则引擎不提供数据库查询能力
- 输入数据由业务系统准备好后传入

✗ **外部系统调用**
- 规则引擎不直接调用外部API
- 如需调用，在ActionHandler中实现

✗ **复杂计算**
- 规则引擎不适合复杂的数学计算
- 复杂计算应在业务系统完成后传入

✗ **事务管理**
- 规则执行不保证事务性
- 事务由业务系统控制

#### 3.2.2 暂不支持（未来可扩展）

✗ **决策表可视化配置**
- V1.0暂不支持决策表的可视化配置
- 可通过JSON或DRL手工编写

✗ **规则流（Rule Flow）**
- V1.0暂不支持规则流程图配置
- 通过优先级和规则组实现简单流程

✗ **规则模板**
- V1.0暂不支持规则模板功能
- 通过规则复制实现类似功能

✗ **规则A/B测试**
- V1.0暂不支持A/B测试
- 可通过规则启用/禁用手动切换

✗ **规则推荐（AI辅助）**
- V1.0暂不支持AI智能推荐规则
- 规则需人工配置

✗ **规则热加载（不重启应用）**
- V1.0规则更新需手动刷新缓存
- 不支持自动热加载

✗ **分布式规则执行**
- V1.0为单机版
- 未来可支持分布式集群

## 四、技术能力边界

### 4.1 性能指标

| 指标 | 目标值 | 说明 |
|-----|-------|------|
| 单次规则执行时间 | < 100ms | 简单规则，输入数据 < 100个字段 |
| 批量执行吞吐量 | > 1000次/秒 | 并行执行 |
| 规则数量支持 | < 1000条/场景 | 超过建议拆分场景 |
| 规则嵌套层级 | < 10层 | 过深影响性能和可读性 |
| 输入字段数量 | < 200个 | 单次执行的输入字段数 |
| 并发用户数 | 100+ | 同时在线用户 |

### 4.2 数据规模限制

| 项目 | 限制 | 说明 |
|-----|-----|------|
| 单条规则条件数 | < 50个 | 超过建议拆分为多条规则 |
| 单个数组长度 | < 1000个元素 | 用于in、contains操作 |
| 字符串长度 | < 10000字符 | 文本字段长度 |
| 规则总数 | < 10000条 | 全系统规则总数 |
| 业务场景数 | < 100个 | 不同的sceneCode数量 |

### 4.3 技术依赖限制

| 依赖 | 版本要求 | 说明 |
|-----|---------|------|
| JDK | 11+ | 必须 |
| Spring Boot | 2.7.x | 必须 |
| Drools | 7.x - 8.x | 核心依赖 |
| MySQL | 8.0+ | 数据库 |
| Redis | 6.0+ | 可选（缓存） |

## 五、扩展性边界

### 5.1 可扩展的部分（✓）

✓ **新业务场景接入**
- 实现BusinessAdapter接口即可
- 无需修改规则引擎核心代码

✓ **新字段类型**
- 在rule_metadata表添加新字段定义
- 前端自动识别并展示

✓ **新操作符**
- 扩展RuleCompiler的操作符转换逻辑
- 前端添加新操作符选项

✓ **新动作类型**
- 实现ActionHandler接口
- 在BusinessAdapter中注册

✓ **新规则类型**
- 扩展RuleCompiler支持新类型
- 如DECISION_TABLE、SCRIPT

✓ **新数据源**
- 在BusinessAdapter的preProcess中集成
- 规则引擎无需感知数据来源

✓ **新输出格式**
- 在BusinessAdapter的postProcess中转换
- 规则引擎无需感知输出格式

### 5.2 不可扩展的部分（✗）

✗ **Drools引擎替换**
- 规则引擎核心依赖Drools
- 更换引擎需要重构核心代码

✗ **规则语言变更**
- 使用Drools DRL语言
- 无法切换到其他规则语言（如Python、Groovy）

✗ **数据结构强类型化**
- 使用Map<String, Object>通用结构
- 无法改为强类型POJO（会失去通用性）

## 六、业务能力边界

### 6.1 适合的业务场景

✓ **规则判断类场景**
- 传染病报卡识别
- 处方审核
- 病案质控
- 临床路径匹配
- DRG/DIP分组

✓ **条件触发类场景**
- 满足条件触发告警
- 满足条件自动执行某动作
- 多维度条件综合判断

✓ **规则频繁变化的场景**
- 政策法规变化
- 医院内部制度调整
- 需要快速响应变化

✓ **需要可视化配置的场景**
- 业务人员自行配置规则
- 减少对开发人员的依赖

### 6.2 不适合的业务场景

✗ **复杂流程控制**
- 多步骤审批流程
- 工作流引擎更合适

✗ **实时计算密集型**
- 大量数学计算
- 复杂算法（如机器学习）

✗ **需要状态管理**
- 多轮对话
- 长时间会话

✗ **强实时性要求（毫秒级）**
- 规则执行需要一定时间
- 不适合超低延迟场景

✗ **高度定制化逻辑**
- 每个案例逻辑都不同
- 无法抽象为规则

## 七、安全与权限边界

### 7.1 支持的安全能力

✓ **接口鉴权**
- 基于Token的身份验证
- 接口访问权限控制

✓ **数据隔离**
- 不同场景数据隔离
- 不同规则组数据隔离

✓ **操作审计**
- 记录规则创建、修改、删除操作
- 记录操作人和操作时间

✓ **敏感数据脱敏**（需业务系统配合）
- 在preProcess中对敏感数据脱敏
- 规则引擎不直接处理原始敏感数据

### 7.2 不支持的安全能力

✗ **细粒度字段权限**
- 不支持基于角色的字段级权限
- 权限控制应在业务系统实现

✗ **数据加密**
- 规则引擎不对数据加密
- 加密应在传输层（HTTPS）或存储层实现

✗ **多租户隔离**
- V1.0不支持SaaS多租户
- 不同租户需部署独立实例

## 十一、使用建议

### 11.1 适合使用规则引擎的情况

1. **规则明确且可枚举**: 规则可以用条件表达式清晰描述
2. **规则变化频繁**: 避免频繁修改代码和发布
3. **需要业务人员参与**: 提供可视化配置界面
4. **多维度条件判断**: 需要组合多个数据源
5. **需要统一管理**: 多个业务场景共享规则管理平台

### 11.2 不适合使用规则引擎的情况

1. **规则高度个性化**: 每个案例逻辑完全不同
2. **需要复杂计算**: 涉及大量数学运算和算法
3. **强实时性要求**: 需要毫秒级响应
4. **流程化业务**: 多步骤审批流程，应使用工作流引擎
5. **一次性规则**: 规则不会变化，写死在代码中更简单

### 11.3 最佳实践

1. **规则粒度适中**: 不要过细也不要过粗
2. **避免过度嵌套**: 条件嵌套不超过5层
3. **合理使用优先级**: 确保规则执行顺序可控
4. **充分测试**: 每条规则都要有测试用例
5. **定期评审**: 定期检查规则有效性，清理无效规则
6. **文档化**: 重要规则添加详细说明
